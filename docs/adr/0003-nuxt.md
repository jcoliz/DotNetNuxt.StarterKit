# 0003. Using Nuxt

Date: 2026-10-01

## Status

Accepted

## Context

Plain Vue gives you a rendering library, but leaves routing, project structure, build configuration, and deployment target to you. Nuxt is the common meta-framework for professional Vue sites, in the same way Next.js is for React.

## Decision

Build the frontend with **Nuxt**, deployed as a **statically generated site** (`nuxt generate`).

Static generation is the key reason. The built frontend is a folder of static files that can be hosted on any static host or CDN, with no Node.js server at runtime. This pairs it with a conventional .NET API backend ([0001](0001-spa-web-app.md), [0006](0006-production-infrastructure.md)).

> **Implementation status:** The frontend (`src/FrontEnd.Nuxt`) is not yet implemented. Only the API client base class (`app/utils/AuthorizedApiBase.ts`) is present so far. This ADR describes what the frontend will use.

## What Nuxt provides

### File-based routing

Routes are generated from the `pages/` folder, with no router configuration.

```
pages/
  index.vue          → /
  about.vue          → /about
  users/
    [id].vue         → /users/:id
```

### Auto-imports

Vue APIs, composables, and components are imported automatically.

```vue
<script setup>
const count = ref(0)       // ref is auto-imported
const router = useRouter() // so are Nuxt composables
</script>

<template>
  <MyComponent />          <!-- auto-imported from components/ -->
</template>
```

### Layouts

Shared page chrome lives in `layouts/`. `default.vue` is used automatically; other pages opt in with `definePageMeta({ layout: 'admin' })`.

### Data fetching composables

`useFetch`, `useAsyncData`, and friends provide loading, error, and refresh state. In this stack most API access goes through generated API clients instead (see [0012](0012-component-data-fetching-pattern.md)).

### Middleware / route guards

```typescript
// middleware/auth.ts
export default defineNuxtRouteMiddleware((to, from) => {
  // redirect unauthenticated users
})
```

### Modules

One-line integration for UI libraries, state management (Pinia), utilities (VueUse), and more, registered in `nuxt.config.ts`.

### TypeScript

Types for routes, composables, and components are generated automatically.

### Deployment flexibility

The same app can be built for static hosting, Node.js SSR, edge/serverless, or plain SPA mode, with minimal config changes.

## Consequences

### Easier

- Less boilerplate and fewer decisions to make for project structure
- Static hosting is cheap and the frontend can be served from a CDN
- Good developer experience: Vite-powered HMR and Nuxt DevTools
- The deployment target can change later without rewriting the app

### More difficult

- Nuxt adds its own conventions and abstractions to learn on top of Vue
- Node.js tooling is required even for developers who mostly work on the backend
- Static generation means no request-time server rendering. Pages that need per-request server logic need a different approach (e.g. the .NET backend).
- Nuxt's built-in server routes (`server/api`) are not used. The .NET backend is the API (see [0010](0010-backend-for-frontend.md)).

### When to use plain Vue instead

Plain Vue is a better fit for a component library, a widget embedded in an existing non-SPA site, or when you need full control of the build.
